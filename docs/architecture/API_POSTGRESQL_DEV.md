# API PostgreSQL de Desenvolvimento

## Objetivo da etapa

Esta etapa valida a persistencia real da nova API usando FastAPI, SQLAlchemy 2.x assincrono, asyncpg, PostgreSQL e Alembic.

O aplicativo desktop continua usando SQLite como banco oficial. Nenhum dado real foi migrado e nenhuma regra funcional de propostas, producao, galvanizacao, expedicao, fiscal ou cargas foi implementada na API.

## Arquitetura atual

```text
API FastAPI
  -> SQLAlchemy AsyncEngine / AsyncSession
  -> PostgreSQL de desenvolvimento
  -> Alembic para estrutura versionada
```

A API tambem continua iniciando sem `DATABASE_URL`, em modo de fundacao, para manter a evolucao gradual.

## Docker

O ambiente preferencial usa Docker Compose:

```text
docker-compose.dev.yml
```

A partir da Etapa 3.1, o runtime oficial de desenvolvimento e API + PostgreSQL no Docker. O Windows deve acessar a API por HTTP em `http://127.0.0.1:8000`, e a API deve acessar o banco internamente pelo hostname `postgres`.

Detalhes completos:

```text
docs/architecture/API_RUNTIME_DEV.md
```

Antes de iniciar, defina uma senha local fora do Git:

```bat
set POSTGRES_PASSWORD=sua_senha_local
set POSTGRES_DB=controle_producao_dev
set POSTGRES_USER=controle_dev
set POSTGRES_PORT=55432
scripts\start_dev_environment.bat
```

O arquivo versionado exige `POSTGRES_PASSWORD` via variavel de ambiente e nao armazena senha real.

Alternativa Windows: instalar PostgreSQL localmente, criar o banco `controle_producao_dev`, criar um usuario local de desenvolvimento e configurar `DATABASE_URL` no arquivo `api\.env`.

## Arquivo .env

Crie `api\.env` localmente com valores reais apenas no computador de desenvolvimento. Esse arquivo e ignorado pelo Git.

Exemplo conceitual:

```env
APP_ENV=development
DATABASE_URL=postgresql+asyncpg://controle_dev:SENHA@127.0.0.1:5432/controle_producao_dev
DATABASE_POOL_SIZE=5
DATABASE_MAX_OVERFLOW=10
DATABASE_CONNECT_TIMEOUT=10
DATABASE_POOL_TIMEOUT=30
DATABASE_POOL_RECYCLE=1800
DATABASE_ECHO=false
```

Os logs e respostas da API nao devem exibir usuario, senha, host, porta ou URL completa.

## Iniciar API

```bat
scripts\start_dev_environment.bat
```

O script antigo `scripts\start_api_dev.bat` permanece apenas como alternativa local nao recomendada.

## Migrations

Aplicar:

```bat
scripts\run_api_migrations.bat
```

Consultar revisao e historico:

```bat
scripts\api_revision_dev.bat
```

Executar manualmente a partir de `api`:

```bat
python -m alembic upgrade head
python -m alembic current
python -m alembic history
python -m alembic downgrade base
python -m alembic upgrade head
```

A API nao executa migrations automaticamente no startup.

## Banco dev e banco test

Banco de desenvolvimento sugerido:

```text
controle_producao_dev
```

Banco de testes sugerido:

```text
controle_producao_test
```

Testes destrutivos exigem:

```bat
set POSTGRES_PASSWORD=sua_senha_local

```

Os testes de integracao recusam execucao se `APP_ENV` nao for `test`, se a URL nao for PostgreSQL asyncpg ou se o nome do banco nao contiver `test`.

## Padrao de IDs

Padrao escolhido para novas tabelas da API:

```text
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

Justificativa:

- o sistema legado SQLite ja usa IDs inteiros;
- a migracao gradual podera preservar os IDs existentes com menor atrito;
- relacionamentos e auditoria ficam mais faceis de depurar durante a transicao;
- novas tabelas podem receber colunas `legacy_id` quando precisarem rastrear registros importados do SQLite;
- se no futuro houver necessidade distribuida, identificadores externos UUID podem ser adicionados sem quebrar a chave primaria operacional.

## Estrategia para IDs legados

Durante a migracao SQLite -> PostgreSQL, tabelas funcionais poderao manter o ID original em uma coluna `legacy_id` ou preservar o proprio ID quando tecnicamente seguro.

A decisao sera feita por modulo, considerando chaves estrangeiras, historico, auditoria e compatibilidade temporaria com o desktop.

## Readiness

`GET /api/v1/system/ready` responde:

```json
{"status":"ready","database":"not_configured","mode":"foundation"}
```

quando nao ha banco configurado.

Com banco configurado, conectado e na revisao esperada:

```json
{"status":"ready","database":"connected","mode":"development"}
```

Com banco indisponivel ou revisao incompativel, retorna `503` com erro padronizado.

## Versionamento

`GET /api/v1/system/version` retorna a versao da API, estagio, revisao Alembic atual e status de compatibilidade.

Revisao esperada nesta etapa:

```text
20260720_0001
```

## Diagnostico de conexao

Verifique:

- container ativo com `scripts\status_postgres_dev.bat`;
- `DATABASE_URL` definida apenas localmente;
- banco correto para dev ou test;
- senha local correta;
- porta livre;
- migration aplicada com `scripts\api_revision_dev.bat`.

## Parar ambiente

```bat
scripts\stop_postgres_dev.bat
```

Para remover volumes de desenvolvimento, use Docker Compose manualmente com cuidado:

```bat
docker compose -f docker-compose.dev.yml down -v
```

Isso remove dados locais do PostgreSQL de desenvolvimento.

## Cuidados contra producao

- nao usar `APP_ENV=production` nos scripts de desenvolvimento;
- nao colocar senha real em arquivos versionados;
- nao apontar `POSTGRES_TEST_DATABASE_URL` para banco sem `test` no nome;
- nao usar banco de producao para testes;
- nao alterar o SQLite oficial nesta etapa.

## Debitos tecnicos SQLite identificados

Durante a suite antiga foram observados `ResourceWarning` relacionados a conexoes SQLite durante testes de migrations legadas.

Origem observada:

```text
app/services/migration_runner.py:126
tests/test_fiscal_migration.py
tests/test_migrations.py
```

A causa provavel e alguma conexao SQLite legado permanecendo aberta durante cenarios de migration. Como essa area pertence ao desktop e a etapa atual e focada na API/PostgreSQL, nenhuma refatoracao ampla foi feita agora. O ponto deve ser tratado em uma etapa propria de saneamento do legado, com testes especificos para fechamento de conexoes.

## Limitacoes desta etapa

- nenhuma autenticacao completa implementada;
